Does replay capacity change FlashSAC's Cartpole stability?

Pristine official Torch FlashSAC, two capacities, two paired seeds, one GPU allocation.

Abstract

131,072 transitions: 0/2 final gate passes; 0/2 passed at both 900 and 1000. Mean final settled upright time was 2.51%.

10,000,000 transitions: 2/2 final gate passes; 2/2 passed at both 900 and 1000. Mean final settled upright time was 100.00%.

This is a bounded descriptive pilot. Capacity is the only configured treatment; neither improvement nor quality equivalence is assumed.

The previous 10,000-iteration study showed temporary balancing followed by regressions. Replay capacity was an unconfirmed explanation for that instability, which motivated this capacity-only pilot.

What was measured

Four fresh 1,000-iteration runs, 1,024 worlds and 16 steps/iteration: 16,384,000 transitions/run. Only replay capacity changes: 131,072 versus 10,000,000. The latter first fills at iteration 611; evaluations 600/650 bracket this. All 44 common evaluations use the same 128 original states and permanently masked first episodes. The frozen gate requires 95% clean five-second completion and 95% upright time within 0.2 rad after one-second settling. Survival alone is not balancing.

Methods and limits

  • Same Isaac manager Cartpole/Newton-MJWarp MDP, assets, initial weights per seed, reset states, ±1 action boundary and terminal observations. This is not the authors' DMC Cartpole task. Only the official Torch learner is measured: Newton physics capture and compiled Torch learning remain separate; the Torch MDP and collection are not one combined graph.
  • Both arms use pristine compiled Torch FP16 AMP, one-step returns, 100,000 warmup transitions, batch 2,048, two critic calls per eligible vector step and fixed 12,800-call decay to the same nonzero learning-rate floor. No learner/network/reward/entropy changes. The 10M arm matches the authors' Isaac launcher capacity, but that launcher uses three-step returns while both arms here retain one-step returns. This is not a full reproduction of the authors' recipe.
  • 98 uniform-action vector steps precede readiness; 15,903 eligible steps yield 31,806 critic and 15,903 actor/temperature attempts/run. Actual AMP skips and physical saved Adam counters were audited.
  • All four seed 0 smokes run first at 64 worlds and batch 256. Production order: seed 0 small→large, seed 1 large→small, at 1,024 worlds and batch 2,048. The first production run can compile new shapes despite smoke preconditioning. Shared disk compiler caches, unlocked clocks and unbalanced cross-seed boundaries remain limitations. Timing is descriptive; a lower loop cost alone does not establish a capacity effect or fully warm throughput. Two seeds on one GPU are not independent-allocation replication or confidence intervals.
  • Every production run starts fresh, with reset optimizer/scaler/replay states and the same canonical weights within each seed. Portable policies are reloaded into the 128-world evaluator. Final full replay is preserved separately; no exact simulator/global RNG continuation is claimed. The 10M tensors need 480 MB of backing storage; pristine exports can serialize full backing storage even in partially filled smokes.
  • First gate times are offline, interval-censored checkpoint availability, not online detection latency. No automatic longer duration or subsequent tuning is authorized by this pilot.
