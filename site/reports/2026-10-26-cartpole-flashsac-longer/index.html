Duration-only learning follow-up · 26 October 2026

Does a longer budget help FlashSAC balance Cartpole?

Pristine authors' Torch FlashSAC and native CUDA FlashSAC, unchanged recipes, four fresh seeds on one NVIDIA RTX PRO 6000 Blackwell Server Edition GPU allocation.

Abstract

Native CUDA FlashSAC used 33.4% less full training-process time than the authors' Torch implementation (median paired ratio; 4/4 matched runs faster). Execution time and successful learning are separate outcomes.

Authors' Torch FlashSAC: 0/4 runs passed the balancing gate at 2,000 iterations; 0/4 passed at both 1,750 and 2,000, and 0/4 passed at any saved checkpoint. No run met the quality gate in this budget.

Native CUDA FlashSAC: 0/4 runs passed the balancing gate at 2,000 iterations; 0/4 passed at both 1,750 and 2,000, and 1/4 passed at any saved checkpoint. All seed outcomes and any later regressions are retained.

This study measures learning, not only update throughput. Four seeds on one allocation do not establish statistical significance, quality noninferiority or broad hardware generalization.

What changed—and what remained fixed

Each of eight fresh runs trains for 2,000 iterations, 1,024 environments and 16 control steps per iteration: 32,768,000 transitions/run. Only duration, the extra saved-policy checkpoints, two-recipe execution order and a final replay export change from the previous experiment. Networks, losses, rewards, reset states, physics, action scale, replay capacity 131,072, one-step returns, two critic attempts per eligible vector step and the 12,800-call learning-rate decay remain fixed. The decay is deliberately not stretched with the longer run.

The 14 common evaluations occur at 0, 50, 100, 150, 200, 300, 400, 600, 800, 1,000, 1,200, 1,500, 1,750 and 2,000 iterations. Every evaluation uses the exact same 128 initial states from the old study. The balancing gate requires 95% clean five-second completion and 95% upright time after one-second settling, with |wrapped pole angle| < 0.2 rad and finite actions. Pole falling does not terminate this task; survival alone is not balancing. Failed first episodes remain failed, and later autoresets never replace them.

Learning stability

Native CUDA FlashSAC seed 1 was the only run to pass any saved checkpoint. It passed at iterations 600, 800, 1,000, then failed every saved evaluation from 1,200 through 2,000. Its deterministic evaluated action RMS (normalized action units) rose from 0.121 at 1,000 to 0.600 at 1,200. This records a loss of balancing stability; it does not establish a cause or show that longer training will recover it.

Methods and limits

  • Current manager Isaac-Cartpole task with Newton/MJWarp, unchanged authored assets/rewards/resets, shared action clip ±1 and pre-reset terminal observations. Physics and learner captures are separate graphs; the Torch MDP is not in one combined captured graph.
  • The authors' implementation is pristine and uses compiled Torch FP16 AMP. Native FlashSAC uses FP16 dense operations with FP32 activations/master/adjoints/Adam, captured fused updates and active fresh gradients; autotuning is off. Rounding, exploration and sampling trajectories can differ. Python 3.12 is outside the authors' declared Python < 3.12 matrix.
  • Same canonical initial weights per seed, fresh/reset optimizers/replay/scalers and all four seeds without early stopping. Official/native runs alternate first/second position twice each; directed within-seed predecessors balance, cross-seed boundaries do not. Smokes and shared disk caches precondition later processes; no isolated cold-start or locked-clock claim.
  • All 14 scored policy checkpoints omit replay and load on 128 evaluation worlds. A separate continuation-final checkpoint preserves the full replay/learner payload at 2,000 for 1,024-world resume, with physical non-replay state identical to the final portable checkpoint. Export cost is included in final checkpoint/loop/process wall. This does not claim exact simulator/global RNG trajectory restoration.
  • First-crossing times use offline evaluation and worker-monotonic portable checkpoint write-finished intervals. They are not online success-detection latency. Sustained 1,750 & 2,000 success and original 300 & 400 success are separate outcomes; all regressions and failures remain reported.
  • The unchanged previous A/B400-iteration results remain separate historical context. Old/new allocation load, compiler caches and stochastic trajectories differ; only the fresh 400-to-2,000 checkpoints trace a common new run. No pooling, tuning, significance or noninferiority claim is made.
  • The Isaac dependency lock is unchanged with the same explicit NumPy 2.3.5 no-deps overlay. Whole artifact SHA, actual saved optimizer counters/AMP skips, finite changed weights, full replay payloads and common evaluation state/observation hashes were independently audited on CPU. Publication additionally requires actual post-retrieval-ACK workflow/task COMPLETED with exit zero.
