Physics engine

Newton

Give Newton a scene, its current state and a command. It computes what happens over the next small interval of time. Repeat that step to see a robot move, a cloth fold or a pile of sand settle.

Build a scene, then move it forward

Imagine a ball falling onto a floor. The ball’s mass and radius are physical parameters. Its height and velocity change over time. Newton stores those two kinds of information separately so you can step or reset the scene with the same model.

  1. Build

    Describe the ball and floor in a ModelBuilder. Call finalize() to turn that description into a simulation-ready Model.

  2. Prepare

    Allocate a State for positions and velocities, and a Control for commands. A falling ball needs no motor input.

  3. Step

    Find where shapes touch, then advance the state by dt. The solver computes the response to gravity and contact, including the floor pushing back.

How this model computes the bounce

Each step spans 0.08 s. The prediction applies a constant downward acceleration of 9.81 m/s². If that prediction crosses the floor, the demo finds the first instant of impact, reverses the impact velocity, scales its magnitude by the bounciness, then applies gravity for the rest of the step. Very small bounces settle into rest.

The diagram uses a one-dimensional contact calculation. The Newton example below uses its collision pipeline and XPBD solver to handle the sphere and plane in 3D.

See one complete Newton step in Python

This XPBD example uses Newton’s collision pipeline. The two state buffers trade places after each step so the next call reads the latest result.

import newton
import warp as wp

builder = newton.ModelBuilder()
ball = builder.add_body(
    xform=wp.transform((0.0, 0.0, 1.0), wp.quat_identity()),
    mass=1.0,
)
builder.add_shape_sphere(ball, radius=0.25)
builder.add_ground_plane()
model = builder.finalize()

state, next_state = model.state(), model.state()
control = model.control()
pipeline = newton.CollisionPipeline(model)
contacts = pipeline.contacts()
solver = newton.solvers.SolverXPBD(model)
newton.eval_fk(model, model.joint_q, model.joint_qd, state)

for _ in range(120):
    state.clear_forces()
    pipeline.collide(state, contacts)
    solver.step(state, next_state, control, contacts, dt=1.0 / 120.0)
    state, next_state = next_state, state

Newton’s introductory tutorial

How collision detection and contact response fit together

Collision detection starts by pruning unlikely pairs, then tests the remaining shapes to get contact geometry such as a normal, contact points and separation. The solver uses that information to compute a response, including friction along the surface. A pair can be accepted for contact processing while it is still slightly separated, depending on the configured margins.

Some solvers generate contacts internally. For example, SolverMuJoCo can use MuJoCo’s contact detection. SolverImplicitMPM samples colliders on the MPM grid as part of its particle solve. The solver determines which contact path and stepping options are available.

Newton’s collision guide

Pick a solver for what needs to move

Newton provides the shared scene and state machinery. A solver supplies the numerical method that advances the state. The choice depends on what is moving, how it deforms and which constraints it needs.

Rigid robot

Links keep their shape and move at joints. MuJoCo-Warp is a common starting point for articulated robots.

Cloth or soft body

Mesh vertices move relative to one another. VBD reduces the error by updating small groups of vertices.

Sand or soil

Material points can separate and flow. Implicit MPM uses a temporary grid to compute how particles push on one another and on colliders.

How one scene can use several solvers

A robot scooping soil has two jobs. One solver advances the joints and rigid links. Another advances the soil particles. With two-way coupling, the rigid solver supplies moving collider information and the particle solver sends reaction back to the rigid bodies. The coupling scheme determines when information is exchanged, which contacts it handles and how strongly the two sides influence each other.

Newton’s solver and coupling guide

Run many copies together

For robot learning, build one scene and replicate it into many Newton worlds. Each copy can have different commands and positions. Newton groups its simulation arrays by world so the solver can process many copies in parallel.

What is shared across worlds?

World-specific bodies and shapes belong to one world and normally collide only within that world. Global shapes can be shared across worlds, as with a common static floor. A single Model holds the arrays for all worlds. It can still store different parameter values per world when a task randomizes masses, friction or other supported properties.

Newton in Isaac Lab

Isaac Lab runs the robot-learning task. Newton advances the physics. Follow a policy command across that boundary and see how Isaac Lab reads the same robot back across thousands of environments.

Follow one joint command

Imagine a reaching policy telling a robot to bend its elbow. The task decides how to interpret the action and how to score the result. Newton works out how far the elbow actually moves once it accounts for the drive, joint limits and nearby objects.

  1. Isaac Lab sets the target

    The action term turns the policy output into a joint command. The asset buffers it, then write_data_to_sim() writes solver-facing targets or efforts.

  2. Newton advances the robot

    The Newton backend uses the model, state, control and configured solver to step the scene for each physics interval.

  3. Isaac Lab reads the result

    The asset exposes batched positions and velocities. The task turns state and sensor readings into observations, rewards and reset decisions.

Newton stores data for every robot together. An ArticulationView finds the robots that match a label pattern, then presents their data in a predictable batch. Isaac Lab uses this to read the same arm’s joints in each environment and reset only the environments that have finished an episode.

Assume model contains one fixed-base arm with two single-axis joints in each of three worlds. Replace the pattern with the labels in your scene. Here a Newton reset writes coordinates and velocities, then recomputes the link kinematics.

import warp as wp
from newton.selection import ArticulationView

arms = ArticulationView(model, pattern="arm*")
positions = arms.get_dof_positions(state)       # (3, 1, 2)
velocities = arms.get_dof_velocities(state)     # (3, 1, 2)
mask = wp.array([False, True, False], dtype=wp.bool, device=model.device)

arms.set_dof_positions(state, wp.zeros_like(positions), mask=mask)
arms.set_dof_velocities(state, wp.zeros_like(velocities), mask=mask)
arms.eval_fk(state, mask=mask)

With multiple arms per world, a mask shaped (world_count, count_per_world) can select individual arms. A one-dimensional world mask selects every matched articulation in each chosen world.

Newton Selection API · Coordinate and velocity setters

How the Isaac Lab binding differs from a raw view

In the Isaac Lab source for this guide, the Newton articulation resolves the configured USD articulation-root path, compiles it as a regular expression and passes it to ArticulationView with free and fixed joints excluded. With one matching robot per world, asset bindings remove the middle axis with [:, 0], so an environment is the first dimension of the task-facing joint data.

The distinction between coordinates and degrees of freedom matters for a ball joint. Newton stores its position as four quaternion components and its velocity as three rotational components. Isaac Lab’s articulation data maps the coordinates into its task-facing joint representation. Regular strided selections can be views into the original Warp arrays. Irregular selections can require gathering into a separate buffer, so use the setters for portable writes.

In a task, prefer the asset interface. Use robot.data.joint_pos for joint positions, robot.set_joint_position_target(...) for an actuator command, or robot.write_joint_state_to_sim(...) for a reset. The backend supplies the Newton-specific bindings.

From velocity to position and strain

Multiply the interpolated velocity by the time step to get the displacement. Newton also uses the spatial gradient of velocity to update material history. The point values persist between steps and the grid is rebuilt as needed.

vₚ ← Σᵢ wᵢₚ vᵢ xₚ ← xₚ + Δt vₚ

Why use both? The particles move with the sand and keep its history. The grid gives neighbors a shared place to work out how stress and contact change their motion.

Squeezing
The cell's area is shrinking. Measured as (how fast the right side moves away from the left) + (how fast the top moves away from the bottom), from the corner velocities. Negative = squeezing. This is the divergence of the velocity, the volumetric part of the strain rate.
Pressure
The cell's answer to squeezing: it pushes its top corners up and bottom corners down (and left/right apart) just enough that the area stops shrinking. Sand pressure can only push, never pull, so a cell that is growing gets no pressure.
Shape change
The cell skewing or flattening, for example layers sliding over each other. Flattening does both at once: the area shrinks (squeeze) and the shape changes. Friction resists shape change, but only up to μ × pressure. No pressure means no grip: loose sand flows freely. This cap is the Drucker–Prager rule.
Floor
The solid collider under the material (the rose band in the simulation). A corner touching it may not move down into it. Its downward velocity is removed and its sideways velocity is slowed by wall friction.
Iterating
Fixes conflict. Pressure pushes the bottom corners down into the floor; the floor pushes them back; the cell is squeezed again. The solver repeats both fixes until nothing changes. One pass over every cell and every wall corner is one Gauss–Seidel iteration. In Newton the cell's "pressure + shear" is a full 3D stress, and the cap is the Drucker–Prager yield surface.

Velocity basis: who a particle talks to

The velocity basis is a set of bumps, one per grid node. A particle's weight for a node is the height of that node's bump at the particle. The weights always add up to 100%. They decide how mass and momentum spread to the grid, and how grid velocity is read back. The slopes of the bumps give the velocity gradient, which is where strain rate (and therefore stress) comes from. Drag the particle across a cell line and watch the gradient view. Switch to 3D to see the whole neighborhood a particle really talks to: 8, 27 or 64 nodes.

A one-dimensional Q1 weight has a constant slope on each cell interval. In two or three dimensions the weight is a product of these one-dimensional functions, so its derivative normal to a cell face can jump at the face. The solver uses these derivatives to estimate strain rate. Abrupt changes can show up as stress noise when particles cross cells. B2 and B3 smooth the gradients across faces and touch more nodes.

Strain basis: where stress is allowed to vary

The velocity basis decides how the material can move. The strain basis decides what shapes its push-back (stress) can take. The solver measures the strain rate from the grid velocities. It can only answer with stress that has one of the shapes the strain basis allows, much like a picture can only show detail down to its pixel size.

Each stress value is a full symmetric tensor (6 numbers in 3D). Below we color one component. Left: the strain rate the velocity field really has. Right: the closest field the chosen basis can hold, fitted from the particles in each cell. That fit uses the same particle quadrature Newton uses.

Inside the implicit solve

Step 5 is where the physics happens, so here it is slowly, in four pictures. The short version: the grid velocity starts as free motion. The solver then searches for the stresses (inside the material) and contact pushes (from walls) that bend this velocity until every rule holds. Each stress must stay inside the yield cone, nothing may be squeezed tighter than packed, and nothing may move into a wall.

1Three kinds of unknowns, connected by four arrows

The solve has three groups of unknowns, one per basis. They talk only through these operators, which are just big sparse matrices built in steps 3 and 4.

Velocity v
Starts at the free velocity v* from particle → grid. It is never solved for directly. It is whatever v* plus all the pushes gives.
Stress σ
One per strain node. Through B, a stress measures how its node is being deformed. Through Bᵀ, it pushes the velocity nodes around it to change that.
Contact r
One impulse per contact point. Through H it reads the velocity at the wall, and through Hᵀ it pushes back.
The rules
Each σ must stay inside the yield cone and follow its flow rule. Each r must push, never pull (beyond adhesion), and stay within the friction cone. The answer is the set of σ and r where all rules hold at once.

2One strain node's turn: guess, then project onto the yield cone

When a strain node gets its turn, it does two things.

  1. Guess. It reads its current strain rate through B. It then computes the stress change that would cancel that strain rate completely: change = −(strain rate) ÷ W. W = B M⁻¹Bᵀ is the Delassus number. It says how much a unit stress at this node changes this node's own strain rate. In the one-cell zoom above, W = 2, so a pressure of 0.75 cancels a squeeze of 1.5. That guess is the trial stress.
  2. Project. The trial stress may be impossible for sand: too much shear for its pressure, or a pull. If so, it is moved to the nearest allowed stress on the Drucker–Prager cone. The part that was cut away becomes plastic flow: the material slides or separates instead of holding.

Drag the trial stress (ring) below. The axes are the two numbers that matter for the cone: pressure (how hard the node is squeezed) and the size of the shear stress.

Simplified: the drawing projects straight to the nearest point. Newton projects with each node's Delassus metric and its flow rule (dilatancy), in the full 6-number stress space, and also has a pressure cap (p_max). The three outcomes are the same.

3Many nodes at once: graph coloring

Updating one strain node at a time (Gauss–Seidel) converges fast but is sequential. A GPU wants thousands of updates at once. Two nodes can update together only if they share no velocity node. Otherwise both would push the same node based on old information and overshoot. So Newton colors the strain nodes, so that no two of the same color touch a common velocity node. It then updates one color at a time, all nodes of that color in parallel. Hover a cell to see which velocity nodes it touches and which cells it conflicts with.

Wider velocity stencils need more colors. With Q1 a P0 cell touches 2 nodes per axis, so cells two apart are safe: 4 colors in 2D, 8 in 3D. B2 needs 9 / 27 colors and B3 needs 16 / 64. That is why solver="auto" switches to gs-batched for B2/B3. It merges colors into a few batches and splits each shared node's mass between the cells that touch it, Jacobi-style, to stay stable.

4How fast it converges

Each sweep fixes a bit and disturbs a bit, so the error shrinks over many sweeps. The full step in Newton

Notation: particle p with volume Vp, density ρp, velocity vp; velocity node i with weight wip = Ni(xp); strain node k with basis τk; Δt the time step.

  1. Bin particles and build the sparse grid

    Find each particle's cell, activate only cells that hold particles (a NanoVDB sparse grid by default), then build the three function spaces on those cells: velocity, strain and collider. Particles become the integration points of every grid integral below, each with weight Vp.

    step() · _make_grid_basis_space · _make_pic_basis_space

  2. Particle → grid: mass and momentum

    m_i = Σ_p w_ip ρ_p V_p p_i = Σ_p w_ip ρ_p V_p [ v_p + Δt (g + f_p/m_p) + C_p (x_i − x_p) ] v*_i = p_i / (m_i + drag)

    Gravity and external forces enter here, before the solve. C_p is the particle's velocity gradient from the last step (the APIC term; dropped with transfer_scheme="pic"). Particles with density 0 act as kinematic boundaries with infinite mass. air_drag keeps nearly empty nodes from blowing up.

    integrate_mass · integrate_velocity · integrate_velocity_apic · free_velocity

  3. Assemble the strain system on strain nodes

    (B v)_k = Σ_p V_p τ_k(x_p) : Δt sym(∇v(x_p)) strain increment at node k C = compliance (elasticity, damping) per strain node Y_k = yield params (friction, cohesion, p_max…) averaged from particles

    B maps grid velocities to a strain increment at each strain node. This is where the velocity basis gradients meet the strain basis. Elastic strain from the previous step goes into the right-hand side; critical packing adds a unilateral offset.

    strain_delta_form · compliance_form · strain_rhs · integrate_yield_parameters

  4. Sample colliders at the collider basis

    Each collider point gets a signed distance, normal, collider velocity, friction and adhesion. A collider matrix H maps velocity nodes to those points. With pic bases the points are particle centers and velocities are read with the velocity-basis weights.

    Config.collider_basis

  5. Implicit rheology + contact solve

    v = v* + M⁻¹ ( Bᵀσ + Hᵀr ) σ_k inside the Drucker–Prager yield surface, plastic flow along its rule r Coulomb friction at each contact point (no velocity into the wall)

    This is the heart of the solver. See the implicit solve for the step-by-step pictures. In short: unknowns are stresses σ (one per strain node) and contact impulses r. The solver precomputes the diagonal blocks Wkk = BkM⁻¹Bkᵀ (the Delassus operator), rotates each into normal/tangential parts, then sweeps: read the local strain rate from current v, project the stress onto the yield surface, push the change back into v. Strain nodes are colored so non-touching ones update in parallel. Contacts get the same treatment. Nesterov momentum speeds up convergence. It stops at tolerance (1e-4) or max_iterations (250). solver="auto" picks gs for Q1 and gs-batched for B2/B3.

    solve_rheology · _DelassusOperator · _GaussSeidelSolver · _resolve_solver_spec

  6. Grid → particle: velocity, gradient, position

    v_p = Σ_i w_ip v_i ∇v_p = Σ_i v_i ⊗ ∇w_ip (becomes C_p for the next APIC transfer) x_p ← x_p + Δt v_p (speed clamped for CFL safety)

    advect_particles

  7. Update particle material state

    Jp ← Jp · exp(rate · tr Δε_plastic) hardening / softening F_e ← F_e + (Δε_elastic + skew(Δt ∇v_p)) F_e rotation from the skew part σ_p ← project(σ(x_p), yield surface) stored for warm start

    The skew (rotational) part of the velocity gradient never creates stress. It only rotates the stored elastic strain.

    update_particle_strains · update_particle_frames

VBD: moving one vertex at a time

SolverVBD simulates cloth, soft bodies, cables and rigid bodies. VBD (Vertex Block Descent) works directly on the mesh: every vertex, in turn, jumps to the spot where its own forces balance, while its neighbors hold still. Repeat that a few times per step and the whole mesh settles into the implicit-Euler answer, with no big linear system to solve.

vertices / particles Newton step of one vertex elastic energy (stretch, bend, volume) contacts and colliders
Part 1

What VBD is solving

An implicit Euler step can be written as one question: where should every vertex be at the end of the step? The answer is the set of positions x that makes this number as small as possible:

G(x) = Σ_i m_i / (2 h²) · |x_i − y_i|² + E(x) └───── inertia ───────┘ └ elastic + contact energy y_i = x_i + h v_i + h² g (where vertex i would go with no forces: its inertia target)

Inertia pulls each vertex toward its target y, the place momentum and gravity would carry it. Elastic energy E pulls it toward shapes the material likes: rest lengths, rest angles, rest volume. The minimum of G balances both. That balance point is exactly the implicit Euler result, which is why VBD stays stable with large time steps.

VBD finds that minimum by block coordinate descent. It picks one vertex, freezes everyone else, and moves that vertex to the bottom of its own little bowl with one Newton step. Then it moves the next vertex, and so on. Try one such step below.

Part 2

The step, live

A 2D toy that runs the same loop as Newton: predict each vertex's inertia target, then sweep the vertices color by color, giving each one its Newton step, for a fixed number of iterations. Finally, velocity = distance moved ÷ h. Press Next to walk through it, one color at a time.

Try 1–2 iterations: the rope stretches like rubber, because VBD stopped before reaching the minimum. Under-converged VBD looks softer rather than blowing up. Then switch to "all at once": with the same iterations it stretches more, because every vertex reacts to stale neighbor positions. Raising stiffness without raising iterations barely helps; the solver needs more sweeps to pass the stiffness through the chain.

Coloring
Two vertices that share an element (a spring, triangle, tet or bending edge) must not move at the same time, or both would react to stale positions. The rope's elements reach two vertices away, so 3 colors suffice. The net needs 4. Newton requires ModelBuilder.color() before creating the solver.
Iterations

Material modelsStretch, bending, soft bodies and rods
Part 3

Materials: what E(x) is made of

Each material adds an energy, and VBD needs only two things from it per vertex: the force (how energy drops as the vertex moves) and the 3×3 Hessian (how curved that is). A vertex sums these over every element it belongs to.

aCloth stretching: stable Neo-Hookean membrane

Each cloth triangle compares its current shape to its rest shape through the deformation gradient F, a small matrix that maps rest edges to current edges. Two numbers come out of F: Ic (how much the triangle is stretched overall) and J (area ratio: 1 = same area). Drag the corners.

ψ = μ/2 (I_c − 2) + λ'/2 (J − α)² λ' = λ + μ α = 1 + μ/λ' force on corners = −area · ∂ψ/∂x

In Newton, tri_ke is μ (resists shape change), tri_ka is λ (resists area change) and tri_kd damps the rate of FᵀF. Damping on FᵀF ignores rotation, so a spinning cloth is not slowed down. The α shift makes the rest shape force-free. In 3D, F is 3×2 and J = |f₀ × f₁|. Folding a sheet over is not "inverting" it, so J has no sign.

bCloth bending: dihedral angle

Two triangles that share an edge form a hinge. The bending energy only cares about the angle θ between their normals. Look along the shared edge (it is the dot in the middle).

E = ½ k (θ − θ_rest)² k = edge_ke · rest edge length θ = atan2((n₁ × n₂)·e, n₁·n₂)

Scaling by edge length keeps bending stiffness independent of mesh resolution. The Hessian keeps only the positive outer-product part (Gauss–Newton), so it never destabilizes the vertex solve. edge_kd damps the angle's rate of change. Flat cloth has θ_rest = 0; a pre-folded garment stores its rest angles.

cSoft bodies: stable Neo-Hookean tetrahedra

A volumetric soft body is filled with tetrahedra. Each has a 3×3 F and J = det(F) = volume ratio. Below: the energy of one tet scaled uniformly by s (J = s³), including s < 0, where the tet is turned inside out.

ψ = μ/2 (I_c − 3) + λ'/2 (J − α)² λ' = λ+μ, α = 1+μ/λ' P = μ F + λ' (J − α) cof(F)

The classic model has a log(J) term that goes to infinity as a tet collapses and is undefined once it inverts. The stable version (Smith et al. 2018) stays finite and smooth, and it still pushes an inverted tet back out. Newton stores tet_materials = (k_mu, k_lambda, k_damp). Its 3×3 vertex Hessian drops a term that is exactly zero for single-vertex blocks.

dSprings

f(on x₀) = k (l₀ − l)/l · (x₀ − x₁) H = k [ I − (l₀/l)(I − d̂d̂ᵀ) ] damping: −(kd/h)(Δl) d̂

Plain distance springs (spring_stiffness, spring_damping). Under compression (l < l₀) the sideways part of H turns negative. Newton keeps the full H and relies on the det(H) guard; many codes clamp it.

eCables and rods: capsules joined by rod joints

Newton's cables are not particle chains. ModelBuilder.add_rod() builds a chain of rigid capsule bodies connected by ROD joints, and VBD solves them on its rigid-body side (Part 5). Each joint measures two things in the parent capsule's frame:

Stretch / shear
u = Rₚᵀ(x_c − x_p) = [shear_x, shear_y, stretch_z], resisted by (shear_stiffness, shear_stiffness, stretch_stiffness). Defaults: stretch 1e5, and shear follows stretch.
Bend / twist
A discrete-elastic-rod curvature κ = [bend_x, bend_y, twist_z] relative to a cached rest curvature, resisted by (bend_stiffness, bend_stiffness, twist_stiffness). Defaults: bend 0, and twist follows bend.
Hysteresis
Optional Dahl friction on bending (custom attributes vbd.dahl_eps_max, vbd.dahl_tau) makes cables keep a bit of their bent shape, like a real cable.

Part 4

Contact, friction and never passing through

Cloth must not pass through itself. VBD handles this with three layers: a contact energy that grows steeply as surfaces approach, a smooth friction law, and a hard safety net (Divide and Truncate) that limits every move.

Self-contact push vs distance
Friction vs sliding distance
Contact energy
Vertex–triangle and edge–edge pairs closer than the margin r (particle_self_contact_margin, default 0.2) get a push. From r down to r/2 it is a soft spring, −k(r−d). Below r/2 it becomes a log barrier, kτ²/d, that grows without limit as d → 0. Very close to zero it switches to a quadratic again, so the numbers stay finite. k is model.soft_contact_ke.
Friction
IPC-style smoothed Coulomb: f = μ f_n · ramp(|u|), where u is the sliding since the start of the step. Below ε_u = friction_epsilon · h it acts like a stiff spring (static friction). Above it, it is full Coulomb μ f_n. The ramp keeps the Hessian smooth.
Damping
Contacts damp the rate the gap closes (soft_contact_kd). By default this works in both directions.
Detection
Contact pairs are found before (and right after) the forward prediction by default, then reused through the iterations. They can be refreshed every n iterations.

DATDivide and Truncate: the safety net

A Newton step can overshoot. So after each color, every proposed move is cut back. For each nearby vertex–triangle or edge–edge pair, a dividing plane is placed between them, and neither side may cross it in this update. Moves are also capped at 0.5 · 0.85 · query radius. Because each side stays on its side of a plane, surfaces cannot tunnel through each other, however big the step. Drag the arrow tip.

Newton runs this as _penetration_free_truncation after every color. Each pair lowers a per-vertex factor t with an atomic min, then displacement = t · proposed, clamped to the max move. The relaxation 0.85 is dat_conservative_bound_relaxation. With rigid_soft_enable_dat, rigid bodies and particles are truncated together.

Part 5

Rigid bodies, joints and cables

The same idea scales up from a vertex to a whole rigid body. A body is one "block" with 6 unknowns (3 translation, 3 rotation), so its local solve is a 6×6 Newton step instead of 3×3. Bodies are colored too: bodies that share a joint or contact never update together.

f = m (com* − com)/h² + joint, contact, attachment forces H_ll = m/h² I τ = R I_body θ/h² + torques H_aa = R I Rᵀ/h² (+ tiny regularization) [Δx, Δω] = LDLᵀ solve of the 6×6 [H_ll H_la; H_al H_aa] then com += Δx, q = normalize(dq(Δω) q)

Joints and contacts are stiff, and a plain penalty spring that stiff would need tiny steps. Newton uses a compliant augmented Lagrangian (ALM). Each constraint row behaves like the material spring K in series with a solver penalty ρ, plus a multiplier λ that remembers the force from earlier iterations and steps.

k_eff = Kρ/(K+ρ) s = K/(K+ρ) row force = k_eff · C + s · λ after each iteration: λ ← s (λ + ρ C) next step: λ ← 0.999 · λ (rigid_avbd_gamma)
ρ is automatic
Joint rows use ρ = max(support, 9K), so k_eff ≥ 0.9 K: a joint is almost as stiff as asked. Limits, contacts and attachments use ρ = support, an estimate of what the bodies can take per step (inverse Delassus ÷ h²).
Joint types
BALL, FIXED, FREE, REVOLUTE, PRISMATIC, D6 and ROD. Linear rows measure the gap between the two attachment points; angular rows the rotation vector of the relative rotation. Drives and limits use joint_target_ke/kd and joint_limit_ke/kd.
Body contact
Normal f_n = max(k_eff · depth + λ_n, 0). Friction is projected into the Coulomb disk μ · f_n, and multipliers are projected the same way after each iteration.
Coupling
Inside one iteration, rigid bodies are swept first, then particles. Body–particle contacts and attachments appear in both, so cloth can drape over a box and push it.

    Pinned particles (inv_mass = 0) stay put. Rigid bodies get the same prediction with semi-implicit Euler. With contacts, the predicted move goes through Divide and Truncate.

    forward_step · step()

  2. Detect contacts

    Self-contact (vertex–triangle, edge–edge) and body contacts within margin + gap. By default before and right after the prediction, optionally every n iterations.

    _self_contact_is_due

  3. Iterate (fixed count, default 10)

    Each iteration sweeps rigid bodies color by color (6×6 solves), then particles color by color (3×3 solves), then updates the ALM multipliers of attachments, joints and contacts.

    for each vertex i of this color, in parallel: f = m(y−x)/h² + Σ elastic + springs + contacts + attachments (each with damping) H = (m/h²) I + Σ their Hessians if |det H| > 1e-8: x_i += H⁻¹ f then: Divide-and-Truncate all moves

Isaac Lab: from a policy action to physics and back

Isaac Lab is the robot-learning framework on top of Newton. It builds thousands of copies of a robot scene, turns the policy's actions into motor commands, steps Newton, measures what happened and hands rewards and observations back to the learning algorithm. In the Isaac Lab 3.x revision used here, Newton is the default backend and can run without Isaac Sim.

The RL loop: what one env.step does

ManagerBasedRLEnv.step(action) runs the same fixed sequence for all environments at once, as batched GPU tensors. Watch it below. On the right, 4,096 environments step together; each square is one robot. A rose square marks a robot that reset on the most recent action.

Click a square or enter a world number, queue a fall, then advance to reset. This batch is a teaching model with synthetic episodes. Resets are per robot. A robot that falls (base_contact) or runs out of time (time_out, 20 s) is reset on the same step. The others keep going, so episodes are spread out in time.

Managers
Each concern is a manager configured with terms. Action (scale, offset), Observation (terms + noise), Reward (weighted terms), Termination, Event (randomization at startup, reset, intervals), Command (e.g. target velocity), Curriculum (e.g. terrain level).
Direct envs
DirectRLEnv skips managers: you write _pre_physics_step, _apply_action, _get_dones, _get_rewards, _get_observations yourself. The decimation loop is the same.
New in 3.x
On Newton, apply_action and write_data_to_sim can be registered as pre-actuator callbacks inside the captured graph, so one sim.step() runs the whole decimation loop on the GPU without Python in between.

PPOFrom rollouts to a better policy

rsl_rl's PPO collects num_steps_per_env = 24 steps from every environment: 4,096 × 24 = 98,304 transitions per iteration. It then estimates how much better each action was than expected (the advantage), and runs 5 epochs × 4 mini-batches = 20 gradient steps. The widget shows one environment's 24-step rollout. Click a step to toggle a fall (termination); drag the sliders.

δ_t = r_t + γ(1−d_t) V(s_t+1) − V(s_t) A_t = δ_t + γλ(1−d_t) A_t+1 (computed backwards) time-out: r_t += γ V(s_t) · time_out (bootstrap)

γ sets how far ahead rewards count (0.99 ≈ 100 steps ≈ 2 s at 50 Hz). λ trades bias for variance: 0 trusts the value estimate, 1 uses the real returns. A fall cuts the chain: nothing after it flows back. Time-outs are not failures, so their value is bootstrapped instead.

MDP2 · A compiled learning task

Imagine teaching a cart to balance a pole. The policy chooses how hard to push. Newton computes how the cart and pole move. The task rules define what the policy sees, how it scores, and when to start a new episode. Isaac Lab describes those rules as a Markov decision process, or MDP.

MDP2 compiles the task rules ahead of time. On the Warp path, compatible rules run together in a few GPU kernels. Once the environment captures an eligible control step, it replays the recorded work with fresh actions and state.

Experimental in Isaac Lab. The current environment runs on Newton and the API can change.

Adjust a push and step the physics.

  1. Apply the action and advance Newton

    Each world gets its own push command on the cart's sliding joint. Newton advances the cart and pole using that input.

  2. Evaluate the outcome

    The task scores the result, checks the cart's travel bounds and the episode timer, and computes observations from joint positions and velocities.

  3. Reset the worlds whose episodes ended

    A mask marks the worlds that need a new episode. Reset events change those worlds' initial joint state. Their returned observations describe the new state.

How a task rule binds to scene data

A Term is a reusable calculation. A Reward or Observation binds it to inputs and gives its output a role. For example, the Cartpole task uses a joint-speed term to penalize a fast cart. The input bindings choose the scene's robot and its sliding joint.

from isaaclab_experimental import mdp2
from isaaclab_experimental.mdp2 import mdp

robot = mdp2.Entity("robot")
cart_speed_penalty = mdp2.Reward(
    term=mdp.joint_vel_l1,
    inputs={
        "joint_vel": robot.joint_vel,
        "joint_ids": robot.joints("slider_to_cart"),
    },
    weight=-0.01,
)

MDPBuilder resolves these bindings against the scene schema, validates the task, and finalizes a compiled MDP. The schedule stays fixed while MDPState holds values that evolve, such as episode length, random streams, and term state. mdp.describe() shows the resulting schedule.

How kernel fusion and CUDA graph replay save time

Kernel fusion

A Warp term can provide a wp.func for one world. The compiler combines compatible functions in generated kernels so more task work happens per GPU launch. The Torch backend runs batched term functions and is useful for developing and checking task logic.

CUDA graph replay

Capture records a sequence of GPU operations, including the physics step when it is capturable. Replay submits that sequence again with much less CPU launch work. Host work marked capturable=False runs between captured segments.

If Python chooses a branch during capture, replay submits the GPU work from that branch. If a value must change each step, put it in device state and update its buffer in place. Use verify_capture to compare captured and uncaptured steps on reproducible physics with the same seed and actions.

Run the Cartpole task and check compatibility

From an Isaac Lab checkout and environment with MDP2 available, train the Cartpole policy with RSL-RL and Newton's MJWarp solver.

uv run python scripts/reinforcement_learning/train.py --rl_library rsl_rl \
  --task Isaac-Cartpole-MDP2 physics=newton_mjwarp

The MDP2RLEnv Gym interface works with the same RL wrappers as a manager-based environment. Check the limitations before porting the task itself. In particular, the current environment expects compatible articulation layouts across worlds and supports a subset of the usual actuator models. Confirm capture behavior if the task depends on host callbacks or mutable parameters.
